So that we can collaborate without leaving Bunkai

Technical Context

  • Frontend: Right-side collapsible panel in App Shell (BK-147). Channel header + scrollable message list + composer pinned bottom. Presence dots. Unread separator.
  • Backend: No confirmed chat API endpoints exist. New DB tables required: channels, messages, channel_members.
  • Database: New tables needed — no schema exists yet. Workspace membership model (BK-1) is upstream dependency.
  • External services: Supabase Auth/Postgres/RLS for channel visibility. Supabase Realtime (broadcast) configured but not wired for chat.
  • Integration points: BK-1 (membership), BK-147 (App Shell), Supabase Realtime (delivery).

Evidence-Confirmed Facts

  • Supabase Realtime configured in migration 0043 for broadcast channels.
  • Chat marked as post-MVP in business-model.md — new DB tables not yet in migrations.
  • Workspace membership (BK-1) exists with RBAC ladder (viewer, member, admin, owner).
  • App Shell (BK-147) exists and can host a right-side panel.
  • No confirmed chat API, message delivery pipeline, Realtime subscription, or presence system exists.

4 Refined Acceptance Criteria (24 Scenarios)

AC1 — Real-time message delivery

Positive 1.1: Should deliver a message to all channel members in real time without page refresh

Given Elena and Sara are both members of "Bunkai QA" and have the general channel open.

When Elena sends "Is staging down? My run just stalled".

Then Sara sees the message appear within 2 seconds without refresh. Shows Elena's name and send time.

Positive 1.2: Should display sender name and timestamp on each message

Given A message has been sent by Elena.

When The message renders.

Then Displays Elena's display name and send time in consistent format.

Negative 1.3: Should not deliver messages to non-channel members

Given A user belongs to a different workspace, not a member of "Bunkai QA".

When A message is sent in the general channel.

Then The non-member does not receive or see the message.

Negative 1.4: Should reject empty or whitespace-only messages

Given Elena has the channel open.

When She attempts to send empty or whitespace-only.

Then Message not sent; clear error shown.

Boundary 1.5: Should reject messages exceeding 4000 chars NEEDS CONFIRMATION

Given Elena has the channel open.

When She types 4001 characters.

Then Send button disabled or error shown before/after sending.

Boundary 1.6: Should accept messages at exactly 1 character

Given Elena has the channel open.

When She sends a single character.

Then Message sent and appears in the channel.

Boundary 1.7: Should accept messages at exactly 4000 characters

Given Elena has the channel open.

When She sends exactly 4000 characters.

Then Message sent and appears in the channel.

AC2 — Message history persistence

Positive 2.1: Should display history in chronological order across sessions

Given General channel contains 20 messages.

When Elena signs out, signs back in, opens the channel.

Then She sees the same 20 messages in chronological order.

Positive 2.2: Should load older messages on scroll-up NEEDS CONFIRMATION

Given Channel has more messages than fit on screen.

When Elena scrolls up.

Then Older messages load progressively without losing scroll position.

Edge 2.3: Should maintain ordering under concurrent sends NEEDS CONFIRMATION

Given Elena and Sara send messages at nearly the same time.

When Both messages appear.

Then Deterministic order consistent across all members' views.

AC3 — Workspace roster

Positive 3.1: Should display all workspace members with their roles

Given Workspace has 3 members: Elena, Sara, Mateo.

When Elena opens the roster.

Then All 3 listed with roles (Admin, Member, Viewer).

Positive 3.2: Should show online/offline presence NEEDS CONFIRMATION

Given Elena opens the roster.

When She views the member list.

Then Each member shows presence (green online, gray offline).

AC4 — Viewer read-only access

Positive 4.1: Should allow viewers to read full history

Given Mateo has the viewer role.

When He opens the general channel.

Then Full history is readable without restrictions.

Positive 4.2: Should disable composer for viewers with read-only hint NEEDS CONFIRMATION

Given Mateo has the viewer role.

When He looks at the composer.

Then Composer disabled with hint indicating read-only access.

Negative 4.3: Should prevent viewers from sending via API NEEDS CONFIRMATION

Given Mateo has the viewer role.

When He attempts to send (e.g. via API manipulation).

Then Server rejects with 403 Forbidden.

AC5 — Reconnection catch-up

Positive 5.1: Should show missed messages after reconnection NEEDS CONFIRMATION

Given Elena's connection drops for 2 minutes. Sara sends 3 messages during gap.

When Elena's connection returns.

Then 3 missed messages appear in correct order without page refresh.

Edge 5.2: Should handle extended disconnection gracefully NEEDS CONFIRMATION

Given Elena's connection drops for 30 minutes.

When Her connection returns.

Then Missed messages appear or she is prompted to refresh if gap exceeds catch-up window.

New scenarios from edge cases

Edge E1: Should queue messages sent while disconnected NEEDS CONFIRMATION

Given Elena loses connection while composing.

When She hits send while disconnected.

Then Message queued for delivery on reconnect or user notified of failure.

Edge E2: Should reflect role changes in real-time NEEDS CONFIRMATION

Given Elena is a member with channel open.

When Admin changes her role to viewer.

Then Composer disables without page refresh.

Edge E3: Should validate messages client-side and server-side NEEDS CONFIRMATION

Given Elena types 4001+ characters.

When She attempts to send.

Then Validation prevents send at appropriate layer with clear error.

NFR E4: Should meet delivery latency SLA NEEDS CONFIRMATION

Given 10 members send simultaneously.

When All messages delivered.

Then Latency within agreed SLA (under 2 seconds).

NFR E5: Should load large history within defined time NEEDS CONFIRMATION

Given Channel has 10,000+ messages.

When Member opens the channel.

Then History loads within defined time budget (e.g. under 3 seconds).

NFR E6: Should support keyboard-only navigation NEEDS CONFIRMATION

Given User navigates with keyboard only.

When Interacting with message list, composer, roster.

Then All interactions keyboard-accessible with visible focus (WCAG 2.1 AA).

NFR E7: Should announce new messages to screen readers NEEDS CONFIRMATION

Given Screen reader user has channel open.

When New message arrives or presence changes.

Then Messages announced via live region; presence not color-only (WCAG 2.1 AA).
